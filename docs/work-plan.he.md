# תוכנית עבודה ולמידה — Container Threat Detection Lab

תאריך: 5 באוקטובר 2026 · גרסה: 1.0 · מצב: אושרה על ידי המשתמש; שלב 0 הושלם.

התוכנית מותאמת לניסיון שלך ב־Linux וב־Docker ולהיכרות ראשונה עם Kubernetes. נתקדם יחד, עם הסבר לפני כל פעולה, תרגול קטן ובדיקת תוצאה. התוכנית אושרה ושלב 0 הושלם; האישור אינו הוראה לבצע את כל הפרויקט ברצף ללא השתתפותך.

## 1. התוצאה שאליה נכוון

נבנה מעבדה שמייצרת פעילות אמיתית בתוך קונטיינרים, אוספת ראיות בעזרת Falco ומנתחת אותן ב־Python. המערכת תחבר פתיחה חריגה של קובץ רגיש מדומה וניסיון חיבור ליעד רשת לא צפוי לאירוע אחד, עם ציר זמן והסבר.

נוכיח את האיכות בעזרת תרחישים תקינים וחשודים, בדיקות קצה והשוואה לפני ואחרי שינוי במדיניות. התוצר יהיה קטן מספיק כדי שתוכל להבין כל רכיב ולהסביר את ההחלטות בראיון.

מטרת הלמידה המקצועית: פיתוח ובדיקת מנגנוני זיהוי, הבנת Linux ורשתות, עבודה בקונטיינרים, כתיבת Python ו־Bash ושיפור בעקבות משוב, תוך שימוש בהקשר פעילות בזמן ריצה.

**הגדרת הצלחה:** נוכל להריץ תרחיש מבוקר, להציג את אירועי המקור, להפיק דוח מוסבר, להשוות לתרחיש תקין ולהראות מה הזיהוי יודע ומה הוא עלול להחמיץ.

## 2. היקף, זמן ושיטת העבודה

**ליבת הפרויקט:** Linux VM, Docker Compose, שני כללי Falco מותאמים, קבצי אירועים, תוכנית Python לניתוח, מדיניות מפורשת, תרחישי בדיקה, דוח הערכה ותיעוד.

**הרחבה לאחר השלמת הליבה:** הרצת אותה מעבדה ב־Kubernetes מקומי. היא נכללת בתוכנית הלמידה, אך אינה תנאי להשלמת גרסת Docker.

**זמן משוער:** כ־25–35 שעות לליבה, כולל הסברים ותקלות סבירות. זה מתאים לכחמישה ימים מרוכזים של 5–7 שעות, או ליותר ימים במפגשים קצרים. הרחבת Kubernetes עשויה להוסיף 6–10 שעות. זו הערכת תכנון, לא התחייבות; לאחר בדיקת הסביבה נעדכן אותה.

הגרסה הראשונה תנתח קובץ הקלטה שהושלם. Falco יאסוף פעולות בזמן ריצה, וה־Python ינתח אותן לאחר ההקלטה. כך נוכל לבצע Replay — להריץ את אותן ראיות מחדש באופן שחוזר על עצמו. עיבוד רציף בזמן אמת יישאר הרחבה נפרדת.

כדי לשמור על ההיקף, גרסת הבסיס תשתמש בדוחות JSON ו־Markdown וב־CLI. ממשק גרפי, מסד נתונים, LLM, כתיבת חיישן eBPF, חשבון ענן וחסימה אוטומטית אינם חלק ממנה.

בכל מפגש נפעל במחזור קבוע:

1. נגדיר מה רוצים להשיג ולמה זה חשוב.
2. נסביר את המושגים והפקודות שנדרשים עכשיו.
3. נבצע שינוי קטן ונבדוק את התוצאה.
4. תקבל תרגיל קצר או שינוי קטן לבצע בעצמך.
5. נסכם מה עובד, מה עדיין לא ומה למדת; נעבור לשלב הבא כשתבקש להמשיך.

אישור התוכנית והעצירות בין שלבים נובעים מבקשתך לעבוד יחד באופן לימודי. בתוך שלב לא נבקש אישור נפרד על כל עריכה שגרתית שכבר סיכמנו לבצע.

## 3. מבנה המעבדה והגדרות הזיהוי

| רכיב | תפקיד |
|---|---|
| Linux VM | סביבת העבודה שעליה ירוצו Docker ו־Falco |
| `orders-api` | אפליקציית הדגמה קטנה שמבצעת פעילות תקינה |
| `allowed-api` | יעד HTTP צפוי של האפליקציה |
| `lab-sink` | יעד HTTP מבוקר שאינו ברשימת היעדים הצפויים |
| קובץ `credentials-demo.json` | מידע מדומה שיאפשר לחקור גישה לקובץ רגיש |
| Falco | תצפית על פעולות מערכת והפקת שני סוגי אירועים |
| Python CLI | אימות, סידור, סיווג וחיבור אירועים לדוח |
| תרחישים ובדיקות | אמת מידה להשוואת ההתנהגות המצופה לתוצאה |

שלושת שירותי ההדגמה יהיו ברשת Docker מקומית. "יעד לא צפוי" פירושו יעד שלא הוגדר במדיניות התקשורת של השירות; הוא יכול להיות כתובת פרטית במעבדה. אין כאן דרישה לשלוח מידע לאינטרנט. רשימת היעדים היא מדיניות לזיהוי, ואינה חומת אש שחוסמת תעבורה.

זרימת המידע:

```text
Lab activity -> Falco rules -> raw JSONL
                                  |
                                  v
                  Validate + normalize + sort
                                  |
                                  v
                      Policy + correlation
                                  |
                                  v
                   JSON incident + Markdown report
```

JSONL הוא קובץ טקסט שבו כל שורה מכילה אירוע JSON אחד. Falco יפיק אירועים שהכללים שלנו בחרו, ולא הקלטה מלאה של כל פעולות המחשב. [תיעוד פלט Falco](https://falco.org/docs/concepts/outputs/formatting/)

נגדיר שני סוגי ראיות:

- **S1 — פתיחת קובץ רגיש לקריאה:** פתיחה מוצלחת של נתיב ההדגמה עם הרשאת קריאה. זו אינה הוכחה שבפועל נקראו בתים מהקובץ.
- **S2 — ניסיון חיבור TCP יוצא:** ניסיון של קונטיינר מנוטר ליצור חיבור, עם היעד ותוצאת קריאת המערכת. חיבור שנכשל או עדיין בתהליך לא יוצג כחיבור שהושלם.

כללי Falco ישמרו ראיות רלוונטיות, והמדיניות ב־Python תחליט מה צפוי ומה מצדיק בדיקה. כך נוכל לשנות מדיניות ולהריץ מחדש את אותו קובץ בלי לאבד את האירועים שהושתקו בגרסה קודמת. נבדוק את משמעות השדות בגרסה שתותקן לפי [השדות הנתמכים](https://falco.org/docs/reference/rules/supported-fields/) ו[המאקרואים של Falco](https://falco.org/docs/reference/rules/default-macros/).

התרחיש מתחיל כאשר כבר קיימת יכולת להריץ פקודות בקונטיינר. אנו בוחנים התנהגות לאחר נקודה זו. המסקנה תהיה "רצף חשוד הדורש בדיקה", ולא "הוכחה לגניבת מידע".

## 4. שלב 0 — הגדרת הבעיה ומודל האיום

**משך משוער:** שעה. **תלות:** אישור התוכנית.

**נלמד:** ההבדל בין אירוע גולמי, אות חשוד ואירוע לחקירה; מהו False Positive ומהו False Negative; כיצד מנסחים השערת זיהוי שניתן לבדוק.

**נעשה:**

1. נתאר במשפט את הפעילות התקינה של `orders-api`.
2. נרשום מי אמור לגשת לקובץ ולאילו שירותים האפליקציה אמורה להתחבר.
3. נתאר רצף חשוד אחד ורצף תקין דומה.
4. נבחר נתיב קובץ, יעדי מעבדה וחלון זמן התחלתי של 60 שניות.
5. נרשום הנחות ומגבלות, ובהן התחלה לאחר קבלת יכולת הרצה בקונטיינר.

**תוצר מתוכנן:** `docs/threat-model.md` עם השערה, פעילות צפויה ושתי דוגמאות.

**תרגול שלך:** להסביר מדוע פתיחת קובץ לבדה יכולה להיות תקינה, ומה מוסיף ההקשר של יעד הרשת.

**תנאי סיום:** ברור מראש מה אמור ליצור אירוע לחקירה ומה לא. אין עדיין טענה על דיוק או יעילות.

## 5. שלב 1 — בחירת סביבת Linux והכנתה

**משך משוער:** 2–4 שעות. **תלות:** שלב 0.

**נלמד:** ההבדל בין Host, VM וקונטיינר; מדוע Falco זקוק לגישה לפעולות ליבת Linux; מה Docker Socket מאפשר ולמה חיישן דורש הרשאות שונות מאפליקציה רגילה.

**נעשה:**

1. נבדוק יחד אם יש סביבת Linux מתאימה, אילו משאבים זמינים ואיזו מערכת וירטואליזציה קיימת. לא נבחר כלי חדש לפני הבדיקה.
2. נשתמש ב־Linux קיים או נקים VM ייעודי למעבדה, עם Docker Engine ו־Compose בתוכו.
3. נוודא זמינות Python, Git וכלי שורת הפקודה הדרושים.
4. נתעד גרסאות, ארכיטקטורה, ליבה ואופן העברת הקבצים בין Windows ל־Linux.
5. נבחר גרסאות מפורשות לרכיבי המעבדה. מימוש הפרויקט יישמר ב־Linux, עם סיומות שורה המתאימות ל־Bash.

מדריך Falco ל־Docker מציין שהמסלול המוצג בו דורש Linux ואינו עובד ישירות ב־Docker Desktop ב־Windows או macOS. לכן Docker Desktop קיים אינו מספיק לבדו לאישור הסביבה. [מדריך Falco הרשמי](https://falco.org/docs/getting-started/falco-docker-quickstart/)

**תוצר מתוכנן:** `docs/environment.md` ומבנה מאגר ראשוני.

**תרגול שלך:** לזהות היכן פועלת כל פקודה — ב־Windows, ב־VM או בתוך קונטיינר.

**תנאי סיום:** קונטיינר בדיקה פועל ב־Linux, ניתן לצפות בלוגים שלו וקיימת דרך ברורה לערוך את קובצי הפרויקט.

**אם נתקעים:** נתחום אבחון תשתית לסבב קצר ונבחר סביבת Linux חלופית אם צריך. אפשר ללמוד את מנתח האירועים עם קלט לדוגמה, אך לא נסמן את איסוף האירועים כהושלם בלי תצפית אמיתית.

## 6. שלב 2 — בניית שירותי ההדגמה והפעילות התקינה

**משך משוער:** 2–3 שעות. **תלות:** שלב 1.

**נלמד:** רשת Docker, שמות שירותים ופורטים; תקשורת יוצאת לעומת נכנסת; bind mount לקריאה בלבד; לוג אפליקציה לעומת אירוע מערכת.

**נעשה:**

1. ניצור אפליקציית Python קטנה עם בדיקת בריאות ופעולת הדגמה מוגדרת.
2. נוסיף את `allowed-api` ואת `lab-sink`; שניהם יחזירו תשובה פשוטה ויתעדו טקסט בדיקה בלבד.
3. ניצור קובץ פרטי גישה מדומים ונמפה אותו לשירות הרלוונטי בלבד.
4. נכתוב `compose.yaml` להפעלת הסביבה באופן חוזר.
5. נפיק תיאור של מזהי הקונטיינרים וכתובות היעדים בכל הרצה. לא נניח שכתובות IP נשארות קבועות אחרי יצירה מחדש.

האפליקציה לא תציע endpoint שמריץ פקודות שרירותיות. תרחישי ההדגמה יופעלו בסקריפטים שלנו. Falco יקבל את הגישה הנדרשת בתוך VM המעבדה; שירותי הדוגמה עצמם לא צריכים לרוץ במצב privileged.

**תוצרים מתוכננים:** `lab/compose.yaml`, קוד האפליקציה והשירותים, דוגמת קובץ מדומה וסקריפט תיעוד הסביבה.

**תרגול שלך:** לשנות את יעד האפליקציה בין שני שירותי המעבדה ולזהות בלוגים איזה שירות קיבל את הבקשה.

**תנאי סיום:** הפעילות התקינה ניתנת לשחזור, שני היעדים נגישים, וידוע בדיוק איזה קונטיינר ביצע אותה.

## 7. שלב 3 — קבלת אירועים אמיתיים מ־Falco

**משך משוער:** 2–3 שעות. **תלות:** שלב 2.

**נלמד:** syscall, חיישן eBPF ברמה מעשית, הפרדה בין חיישן לכלל, שדות תהליך וקונטיינר, JSONL.

**נעשה:**

1. נתקין ונפעיל את גרסת Falco שנבחרה; נוודא שהדרייבר וההרשאות מתאימים לסביבה.
2. נגדיר פלט JSON לקובץ ונפריד אותו מהודעות הפעלה ושגיאה.
3. נשתמש בכלל בדיקה זמני ופשוט כדי לראות פעולה על קובץ ההדגמה; בשלב הבא נהפוך את בדיקת התצפית לכלל הסופי.
4. בעזרת כלל בדיקה נוסף נוודא שניסיון חיבור לשירות במעבדה מופיע עם כתובת, פורט ותוצאה ניתנים לפירוש.
5. נשמור דגימה של כל סוג אירוע ונבדוק את מצב החיישן ואת דיווחיו על איבוד אירועים.

**תוצרים מתוכננים:** `falco/falco.yaml`, הגדרת הפעלה, דגימות אירועים ותיעוד גרסאות.

**תרגול שלך:** מתוך אירוע בודד, להצביע על זמן הפעולה, הקונטיינר, התהליך, הקובץ או יעד הרשת.

**תנאי סיום:** יש הוכחה לשני סוגי התצפיות מהקונטיינר המתאים. שדה חסר או איבוד אירועים לא יתפרשו כ"לא הייתה פעילות".

## 8. שלב 4 — כתיבת הכללים והמדיניות הראשונית

**משך משוער:** 2–3 שעות. **תלות:** שלב 3.

**נלמד:** תנאי כלל, רשימות, מאקרואים, סינון לפי הקשר, ההבדל בין התנהגות צפויה לבין הוכחת הרשאה.

**נעשה:**

1. נכתוב כלל S1 שמפיק ראיה על פתיחה מוצלחת לקריאה של הנתיב המדומה בקונטיינרים המנוטרים.
2. נכתוב כלל S2 שמפיק ראיה על ניסיון חיבור TCP יוצא מהם. נכלול יעדים פרטיים, כדי שגם `lab-sink` ייראה.
3. נגדיר בפלט רק שדות שמשרתים את החקירה: זמן מדויק, כלל, מזהה קונטיינר, תהליך ואביו, UID, נתיב קובץ או יעד רשת ותוצאת הפעולה.
4. נכתוב מדיניות ראשונית: תחום קונטיינרים מנוטר, נתיב רגיש, רשימת יעדים צפויים וחלון הזמן.
5. נבדוק תחביר ושדות מול גרסת Falco שהותקנה, ואז נריץ דוגמה אמיתית לכל כלל.

הרשימה תתייחס לצירוף כתובת יעד, פורט ופרוטוקול. לא נגדיר שכל כתובת פרטית בטוחה. שם כמו `python` או `curl` אינו מספיק כדי לקבוע אמינות, וגם פרטי התהליך אינם מוכיחים מי האדם שהפעיל אותו.

**תוצרים מתוכננים:** `falco/rules.yaml`, `config/policy.baseline.yaml` ותיאור קצר לכל כלל: מטרה, ראיות, דוגמה תקינה ומגבלות.

**תרגול שלך:** לשנות פרט אחד במדיניות, לנבא את ההשפעה ואז לבדוק אותה.

**תנאי סיום:** שני הכללים נטענים ופועלים; אפשר לקשר כל התרעה לפעולה שהפעלנו.

## 9. שלב 5 — תרחישים מתויגים והקלטות שאפשר לשחזר

**משך משוער:** כשעתיים. **תלות:** שלב 4.

**נלמד:** Ground Truth — תוצאה מצופה שנקבעת מראש; ההבדל בין בדיקת איסוף לבדיקה של לוגיקת זיהוי; חשיבות קיבוע הקלט להשוואה.

**נעשה:**

1. נכתוב תרחיש תקין: האפליקציה פותחת את קובץ ההדגמה ופונה ליעד הצפוי.
2. נכתוב תרחיש חשוד: פתיחה של הקובץ ואחריה פנייה ל־`lab-sink` עם טקסט בדיקה קבוע.
3. נוסיף דוגמאות של אות בודד, יעד שונה, תהליך אחר ושני קונטיינרים שונים.
4. נגדיר לכל תרחיש מזהה, תיאור, תוצאה צפויה, זמן התחלה וסיום וגרסת המדיניות.
5. נשמור הקלטות אמיתיות. דוגמאות שנבנו ידנית לבדיקות גבול יסומנו כ־synthetic ויישמרו בנפרד.

לוג היעד יאמת שסימולציית הרשת אכן פעלה. המנתח יקבל רק את קלט החיישן והמדיניות; תווית "תרחיש חשוד" לא תהיה חלק מהחלטת הזיהוי.

**תוצרים מתוכננים:** `scenarios/`, תיאור התרחישים ו־`tests/fixtures/` עם מקור הקלט.

**תרגול שלך:** להציע פעילות תקינה שמזכירה את התרחיש החשוד ולנסח ציפייה לפני שנריץ אותה.

**תנאי סיום:** התרחישים מופעלים באופן חוזר, ומפרידים בין כשל בתרחיש, כשל באיסוף וכשל בזיהוי.

## 10. שלב 6 — מנתח האירועים וחיבור הרצף ב־Python

**משך משוער:** 4–5 שעות. **תלות:** שלב 5.

**נלמד:** parsing, validation, normalization, זמן האירוע לעומת זמן עיבודו, state machine קטנה ו־deduplication.

**נעשה בארבעה צעדים קטנים:**

1. נקרא JSONL, נאמת שדות ונמיר אירועים למבנה אחיד. קלט פגום ייספר ויופיע בדוח שגיאות.
2. נסדר הקלטה שהושלמה לפי זמן האירוע, עם מזהה נוסף לשבירת שוויון. נשמור דיוק זמן מספיק לבדיקת גבולות.
3. נפעיל את מדיניות ההקשר ונחבר ראיות לפי החוזה המפורט להלן.
4. נפיק JSON מובנה ודוח Markdown קריא עם הסיבה להתרעה והפניות לראיות המקור.

**חוזה החיבור לגרסה הראשונה:**

- המפתח הוא מזהה הרצת החיישן, Host ומזהה קונטיינר. שם תצוגה או PID לבדם אינם מפתח מתאים.
- לכל ניסיון חיבור ליעד לא צפוי נחפש את פתיחות הקובץ שהתרחשו באותו קונטיינר ב־60 השניות שקדמו לו. ההפרש חייב להיות גדול מאפס וקטן או שווה ל־60 שניות. זהו חלון חיפוש נע, ולא חלון קבוע שנפתח פעם אחת.
- נבדוק את מדיניות ההקשר על כל זוג של פתיחת קובץ וניסיון חיבור. חריג הכולל יעד רשת יחול רק על זוג הראיות המתאים; הוא לא יהפוך את כל פעולות הקובץ של אותו תהליך לצפויות.
- אם נותר לפחות זוג אחד שלא הוגדר כצפוי, נפיק אירוע אחד עבור ניסיון החיבור ונצרף אליו את פתיחות הקובץ הרלוונטיות. זוג שהוחרג יישמר עם סיבת ההחרגה ולא יסתיר זוג אחר.
- ניסיונות חיבור אמיתיים נוספים יכולים ליצור אירועים נוספים. איגוד שלהם לתקרית ממושכת הוא הרחבה; מניעת כפילויות בליבה מתייחסת לעיבוד חוזר של אותה ראיה.
- חיבור שקדם לפתיחת הקובץ לא מצטרף לרצף. אם זמני המקור זהים בדיוק, נשמור את הראיות אך לא נקבע אוטומטית רצף של "אחרי". שורות שהגיעו בסדר שונה יסודרו לפי זמן המקור.
- כפילות של אותה ראיה לא תייצר התרעה נוספת. שני אירועים אמיתיים דומים יישמרו כנפרדים.
- מזהה קונטיינר או זמן חסרים ימנעו חיבור ויופיעו כבעיית נתונים. שם תהליך חסר לא יהפוך את האירוע אוטומטית לתקין.
- לא נדרוש PID זהה: פעולת קובץ ופעולת רשת יכולות להתרחש בשני תהליכים. עם זאת, חיבור לפי קונטיינר וזמן אינו מוכיח קשר סיבתי; זו מגבלה מפורשת.

נשתמש במזהה אירוע שכולל הקשר של הרצת חיישן, מספר אירוע/זמן מדויק וסוג כלל. נשמור מיפוי למזהי קונטיינרים מלאים כאשר הוא זמין, ונבדוק שאין עמימות במזהה המקוצר בסביבת המעבדה.

**דוח האירוע יכלול:** מזהה, כלל/מדיניות וגרסתם, קונטיינר, חלון זמן, תהליכים, קובץ, יעדי רשת, תוצאות קריאות המערכת, סיבת החיבור, ראיות מקור ומגבלות. רמת החומרה תהיה כלל החלטה מוסבר; היא לא תוצג כהסתברות מספרית לתקיפה.

**תוצרים מתוכננים:** `src/detector/`, ממשק CLI ודוח אירוע לדוגמה.

**תרגול שלך:** לעקוב ידנית אחרי ארבעה אירועים ולנבא כמה אירועים לחקירה יופקו.

**תנאי סיום:** אותו קלט ואותה מדיניות מפיקים אותה תוצאה; ניתן להסביר כל החלטה מתוך הראיות.

## 11. שלב 7 — בדיקות והערכת איכות

**משך משוער:** 3–4 שעות. **תלות:** שלב 6.

**נלמד:** TP, FP, FN, TN; ההבדל בין בדיקת תוכנה לבין הערכת יכולת זיהוי; כיצד בודקים טענה בלי להתאים את כל הדוגמאות לכלל.

נפריד בין שלוש רמות: בדיקת החיישן והכללים במעבדה, בדיקת המנתח על קלט קבוע, ובדיקה של התהליך המלא מפעולה ועד דוח.

| בדיקה | ציפייה |
|---|---|
| קובץ רגיש ואז יעד לא צפוי בתוך החלון | אירוע משולב אחד |
| פעילות האפליקציה מול יעד צפוי | אין אירוע משולב חשוד |
| פתיחת קובץ בלבד | ראיה בודדת, ללא רצף משולב |
| חיבור לא צפוי בלבד | ראיה בודדת, ללא רצף משולב |
| shell ללא שני האותות | אין רצף משולב |
| האותות בקונטיינרים שונים | אין חיבור |
| אותו שם קונטיינר אך מופע חדש | אין חיבור בין המופעים |
| חיבור לפני פתיחת הקובץ | אין חיבור |
| חיבור בדיוק בגבול 60 שניות | נכלל בחלון |
| חיבור מעבר לגבול | אינו נכלל בחלון הקודם |
| פתיחות ב־0 וב־59 שניות, חיבור ב־61 | מחובר לפתיחה ב־59 שניות |
| שני האותות עם זמן מקור זהה בדיוק | נשמרים, ללא קביעה אוטומטית של רצף |
| שורות לא מסודרות אך זמני מקור תקינים | תוצאה זהה לאחר המיון |
| שכפול מדויק של ראיה | אין התרעה נוספת |
| JSON פגום או מזהה נדרש חסר | שגיאת נתונים מדווחת |
| קובץ שלא נפתח בהצלחה | לא נחשב S1 מוצלח |
| ניסיון רשת שנכשל או עדיין בתהליך | מתואר כניסיון, ללא טענת הצלחה |
| וריאציה חשודה עם כלי/תהליך אחר | נבדק שאין הסתמכות על שם כלי יחיד |
| פעילות תקינה בלתי קשורה באותו קונטיינר בתוך החלון | מדידת מגבלת החיבור; ייתכן FP |

התוצאה המצופה בבדיקות לוגיקה מוכרעות מראש צריכה להתקיים. בדוגמאות שבוחנות מגבלה אמיתית מותר לגלות טעות זיהוי; היא תתועד ולא תוסתר באמצעות שינוי התווית.

נמדוד ברמת תרחיש: TP = תרחיש חשוד שהתריע, FN = חשוד שלא התריע, FP = תקין שהתריע, TN = תקין שלא התריע. מספר התרעות כפולות יוצג בנפרד. אם נציג Precision או Recall, נוסיף את המונים והמכנים, ונסמן מכנה אפס כלא מוגדר. תרחיש שאיסוף הנתונים בו נכשל יסומן invalid, לא TN.

נשמור כמה וריאציות שלא שימשו לכיול הכללים, ונציג תוצאותיהן בנפרד. מדובר במדגם מעבדה קטן ולא בהערכת ביצועים בסביבת ייצור.

**תוצרים מתוכננים:** בדיקות `pytest`, מטריצת תרחישים ו־`evaluation/baseline.md` עם ראיות ריצה.

**תרגול שלך:** לחשב מתוך טבלה קטנה אילו שינויים הפחיתו FP והאם הם יצרו FN חדשים.

**תנאי סיום:** בדיקות הלוגיקה עוברות, תרחיש תקין וחשוד אומתו מקצה לקצה, ומגבלות הזיהוי ידועות.

## 12. שלב 8 — שיפור בעקבות משוב לקוח מדומה

**משך משוער:** כשעתיים. **תלות:** שלב 7.

**נלמד:** תהליך בירור התרעת שווא, חריג ממוקד, Regression והפשרה בין הפחתת רעש לכיסוי.

**נעשה:**

1. נוסיף משימת תחזוקה מדומה שקוראת את קובץ ההדגמה ופונה ליעד תחזוקה שלא הוגדר במדיניות הראשונית.
2. נכתוב דיווח לקוח קצר: מה קרה, למה הוא צפוי ואילו ראיות דרושות לאימות הטענה.
3. נגדיר חריג משולב לפי ההקשר שנצפה: workload, נתיב executable/script, משתמש, קובץ ויעד/פורט ספציפיים. הוא ייבדק לאחר יצירת זוג מועמד של פעולת קובץ וניסיון חיבור. כל שדה שנשתמש בו חייב להופיע בנתונים.
4. ניתן למדיניות מספר גרסה ונשמור את גרסת הבסיס.
5. נריץ את שני הנוסחים על אותן הקלטות ועל וריאציות הבדיקה. נבדוק במיוחד את אותו תהליך מול יעד אחר ותהליך אחר מול אותו יעד.

פרטי תהליך ופקודה הם הקשר שניתן לעיתים לחקות; החריג אינו הוכחת הרשאה. גם פעילות שסווגה כצפויה תישמר עם סיבת הסיווג, כדי שניתן יהיה לבדוק אותה.

**תוצרים מתוכננים:** `config/policy.tuned.yaml`, `evaluation/comparison.md` ותחקיר משוב קצר.

**תרגול שלך:** להסביר מדוע חריג כמו "התעלם מכל Python" רחב מדי ולהציע חלופה מצומצמת.

**תנאי סיום:** אפשר לראות מה השתפר, אילו תרחישים חשודים עדיין מזוהים והאם נוצרו החמצות. אם שינוי אינו מועיל, נבטל אותו ונשמור את הממצא.

## 13. שלב 9 — תיעוד, שחזור והצגה בראיון

**משך משוער:** 2–3 שעות. **תלות:** שלב 8.

**נלמד:** כיצד להציג בעיה, החלטה, ראיה ומגבלה; מה ההבדל בין יכולת שמומשה לבין הרחבה מוצעת.

**נעשה:**

1. נכתוב README באנגלית: הבעיה, הארכיטקטורה, דרישות, הפעלה, תרחיש דמו, תוצאות ומגבלות.
2. נצרף תרשים קטן, דוח אירוע לדוגמה והוראות Replay שאינן דורשות חיישן פועל.
3. נכתוב Case Study של עמוד: השערה, ראיות, התרעת שווא, שינוי ותוצאת הבדיקות.
4. נבדוק מחדש הפעלה מהוראות התיעוד בסביבה נקייה של שירותי המעבדה.
5. נכין תסריט לסרטון 2–3 דקות: פעילות תקינה, סימולציה חשודה, ראיות, דוח והשוואת מדיניות.
6. ננסח תיאור לקורות החיים שמתייחס רק למה שהושלם ונמדד.

אפשר למפות את השערת הגישה לקובץ ל־[MITRE ATT&CK T1552.001 — Credentials In Files](https://attack.mitre.org/techniques/T1552/001/). המיפוי מסביר את ההקשר האבטחתי; הוא לא הופך כל פתיחת קובץ להוכחת תקיפה.

**תוצרים מתוכננים:** README, דוח הערכה, Case Study ותסריט/סרטון דמו. פרסום המאגר ייעשה רק כשנגיע לצעד הזה ותחליט לפרסם.

**תרגול שלך:** להסביר במשך שתי דקות מה Falco עושה, מה אתה כתבת ולמה התוצאה אינה מוכיחה דליפה.

**תנאי סיום:** ניתן לשחזר את הדמו מהתיעוד, כל טענה נתמכת בתוצאה, ואתה יכול להסביר את ההחלטות המרכזיות ללא קריאת הקוד.

## 14. הרחבת Kubernetes — שלושה מפגשים לאחר הליבה

**משך משוער כולל:** 6–10 שעות. **תלות:** גרסת Docker עובדת ומתועדת.

**K1 — היכרות והקמת סביבת לימוד.** נלמד Node, Pod, Deployment, Service ו־Namespace דרך השירות שכבר בנינו. נקים cluster מקומי קטן ב־kind בתוך Linux ונפעיל את האפליקציה. תוצר: manifests ויכולת להסביר כיצד בקשה מגיעה לשירות. [סביבות לימוד של Falco, כולל kind](https://falco.org/docs/getting-started/learning-environments/)

**K2 — איסוף אירועים והקשר.** נלמד בקצרה Helm ו־DaemonSet, נתקין Falco ונבדוק את מקור המידע על קונטיינר, Pod ו־Namespace. נעדכן את מיפוי מזהי השירותים ויעדי הרשת; לא נעתיק כתובות Docker כאילו הן עדיין תקפות. תוצר: אירוע אמיתי שניתן לשייך ל־Pod הנכון. שדות העשרה שלא זמינים יוצגו כחסרים.

**K3 — חזרה על ההוכחה.** נריץ תרחיש תקין וחשוד ונבדוק שהמנתח מפיק את התוצאות המצופות. ניצור מחדש Pod ונבדוק שאין חיבור שגוי בין מופעים. תוצר: הוראות הפעלה והקלטות K8s נפרדות. רק לאחר בדיקה זו נוסיף לתיאור הפרויקט תמיכה שנבדקה ב־Kubernetes.

לא נכניס בשלב זה RBAC מורכב, CNI נוסף או מדיניות רשת לאכיפה. נלמד את המושגים הנדרשים להסבר השירות והחיישן ונשאיר נושאים נוספים להמשך.
