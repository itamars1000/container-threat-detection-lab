## 1. כניסה לסביבת העבודה
מתוך PowerShell:
~~~powershell

~~~
בתוך Linux:
~~~bash
cd ~/projects/container-threat-detection-lab

~~~
הנתיב הצפוי: /home/itamar/projects/container-threat-detection-lab.
פרטי הסביבה והגישה מעורך Windows נמצאים ב[סביבת העבודה](environment.md).

התקנת Ubuntu ו־Docker כבר הושלמה. מדריכי ההתקנה המקוריים נשמרו ב־work/docs-archive/2026-10-05/docs.
בהתקנה מחדש יש להתאים את הפקודות למערכת ולגרסאות הזמינות; התיעוד ההיסטורי משקף את ההתקנה שעשינו.

בדיקת המנוע המקומי:

~~~
systemctl בודק אם השירות פעיל. הפקודה השנייה פונה במפורש ל־socket המקומי ומציגה את זהות המנוע.
sudo מפעיל פקודה בהרשאות מנהל; במעבדה משתמשים בו להפעלת Docker.

## 2. רכיבי המעבדה
| שירות | תפקיד |
|---|---|
| orders-api | אפליקציה שקוראת קובץ מדומה ואז פונה לשירות HTTP |
| allowed-api | יעד צפוי לפעילות הרגילה |
| lab-sink | יעד מקומי נגיש שאינו צפוי לפי מודל האיום |

שלושתם מחוברים לרשת Docker פנימית. אין פרסום פורטים למחשב המארח.
כל שירות מאזין בפורט 8080 בתוך הרשת.

הקובץ lab/demo-secrets/credentials-demo.json מכיל ערך מדומה בלבד.
הוא אינו נכלל בהקשר הבנייה וממופה ל־orders-api בלבד, לקריאה בלבד, בנתיב /run/demo-secrets/credentials-demo.json.
השירותים רצים עם UID 10001, מערכת קבצים לקריאה בלבד והגבלות הרשאה המוגדרות ב־Compose.
מיפוי read-only מונע כתיבה דרך המיפוי; הוא מאפשר לקרוא את הקובץ.

## 3. הפעלה ובדיקת השירותים
~~~bash
sudo docker compose -f lab/compose.yaml up -d --build
sudo docker compose -f lab/compose.yaml ps
sudo docker compose -f lab/compose.yaml logs --tail 10 allowed-api
~~~
-f בוחר קובץ Compose. up יוצר או מעדכן שירותים; --build בונה את ה־images; -d מריץ ברקע.
ps מציג מצב. healthy פירושו שבדיקת הבריאות שהוגדרה הצליחה.
בדיקת בריאות אינה הוכחה לתקינות מנגנון הזיהוי.

בלוגים, בקשות מ־127.0.0.1 הן בדיקות עצמיות בתוך קונטיינר השרת.
בקשה מכתובת ברשת Docker יכולה להגיע מקונטיינר אחר. צריך לבדוק את זהותו בזמן האירוע.

תרגיל שכבר בוצע — לקוח זמני:
~~~bash
sudo docker compose -f lab/compose.yaml run --rm --no-deps allowed-api python -c "import socket, urllib.request; print('client:', socket.gethostname()); print(urllib.request.urlopen('http://allowed-api:8080/health', timeout=3).read().decode())"
~~~
run יוצר קונטיינר חדש ומשתמש בהגדרות השירות; הפקודה החלופית מפעילה לקוח Python.
--no-deps מונע הפעלה של תלויות; --rm מסיר את הקונטיינר בתום הפעולה.
שם השירות allowed-api מתורגם ברשת Docker לכתובת השרת. ה־image נשאר גם כשהקונטיינר הזמני הוסר.
אפשר להחליף את כתובת היעד ב־http://lab-sink:8080/health כדי לבדוק את השירות השני.

## 4. רצף הפעילות הרגיל
~~~bash
sudo docker compose -f lab/compose.yaml exec -T orders-api python demo.py
~~~
exec מריץ פעולה בקונטיינר orders-api הקיים. -T מבטל הקצאת מסוף אינטראקטיבי.
demo.py קורא את הקובץ המדומה, בודק את סימון ההדגמה ופונה ל־allowed-api.
הוא אינו שולח את תוכן הקובץ ואינו מדפיס את ערך המפתח.

פלט צפוי:
1. demo_file_read — האפליקציה מדווחת על קריאת הקובץ.
2. http_request_start — תחילת בקשה ל־allowed-api:8080.
3. http_response — תשובת HTTP 200 עם response_service=allowed-api.

פלט exec מוצג במסוף; אין להניח שהוא נשמר בלוגי השירות.
זהו רצף תקין שמייצר שני אותות. זיהוי עתידי צריך להתחשב ביעד הצפוי ולא להתריע רק משום ששניהם התרחשו.

## 6. Falco ובדיקת החיישן
Falco משמש לאיסוף אירועי זמן ריצה מהליבה ולהתאמתם לכללים.
בחרנו בו כדי לקבל ראיות לפתיחת קובץ ולניסיון חיבור, עם פרטי תהליך וקונטיינר ופלט JSON שנוכל לנתח בהמשך.
הוא מספק את האותות; המדיניות והמתאם שנבנה יקבעו אילו רצפים מצדיקים חקירה.

בדיקת חיישן היא ניסוי שבו מבצעים פעולה ידועה ומוודאים שהאירוע המתאים נאסף עם השדות הדרושים.
הצגת גרסה או הודעת startup אינה מספיקה לכך.

~~~bash
sudo docker compose -f falco/compose.yaml up -d
sudo docker compose -f falco/compose.yaml logs --tail 60 falco
~~~
זהו פרויקט Compose נפרד. הוא משתמש ב־modern eBPF ובתוסף container לשיוך.
החיישן פועל בהרשאות privileged לצורך הוכחת ההיתכנות במעבדה.
socket של Docker ממופה לצורך מטא־דאטה; מיפוי socket לקריאה בלבד אינו מגביל את הרשאות פעולות ה־API.
network_mode=none אינו מונע ניטור של פעולות רשת דרך הליבה.

קובצי העבודה:
- falco/compose.yaml — הרצה, מיפויים ופלט.
- falco/preflight-rules.yaml — שני כללי בדיקה זמניים.
- artifacts/falco-preflight/events.jsonl — אירועי כללים; כל שורה היא JSON עצמאי.
- artifacts/falco-preflight/metrics.jsonl — מדדי איסוף בקובץ נפרד.

הודעת השבתת BPF iterators נצפתה באתחול; לאחריה נאספו אירועים בפועל.
יש להעריך את פעולת החיישן לפי הראיות והמדדים ולא לפי שורת לוג בודדת.

## 7. שני הכללים הנוכחיים
**פתיחת הקובץ לקריאה:** open/openat/openat2, דגל פתיחה שמאפשר קריאה, fd.num>=0, נתיב הקובץ המדומה ואירוע מתוך קונטיינר.
זהו אות לפתיחה מוצלחת שמאפשרת קריאה; האירוע לבדו אינו מוכיח שתוכן נקרא.

**ניסיון חיבור TCP:** connect, פרוטוקול TCP, fd.sport=8080, כתובת שרת שאינה 127.0.0.1 ואירוע מתוך קונטיינר.
זהו כלל בדיקה מוגבל לפורט ההדגמה. הוא כולל גם יעד צפוי וגם בלתי צפוי ואינו קובע עוינות.
הוא אינו דורש SUCCESS: יש לשמור ולפרש את תוצאת הניסיון.

בדיקת תצפית חוזרת:
~~~bash
sudo docker compose -f lab/compose.yaml exec -T orders-api python demo.py
sudo tail -n 4 artifacts/falco-preflight/events.jsonl
~~~
tail מציג את סוף הקובץ; הוא אינו מסנן אוטומטית לפי הריצה האחרונה.
בדוק את הזמן, הכלל, מזהה הקונטיינר ואת היעד בכל אירוע.

| שדה | פירוש |
|---|---|
| rule | הכלל שהאירוע התאים לו |
| evt.type / evt.res | סוג הפעולה והתוצאה באותה נקודה |
| evt.rawtime | זמן האירוע בננו־שניות |
| fd.name | נתיב הקובץ |
| fd.cip / fd.cport | כתובת ופורט הלקוח |
| fd.sip / fd.sport | כתובת ופורט השרת |
| proc.cmdline / proc.pid | פקודת התהליך ומזהה התהליך |
| user.uid | המשתמש שביצע את הפעולה |
| container.full_id | זהות מלאה של קונטיינר התהליך |

hostname ברמה העליונה של אירוע Falco שייך לחיישן; הוא אינו hostname של האפליקציה.

## 8. האבחון שביצענו לכלל הרשת
בהתחלה האפליקציה קיבלה HTTP 200, אבל לא הופק אירוע רשת.
כלל אבחון זמני אסף connect ללא סינון הפורט והראה שבאירוע הרלוונטי:
- fd.cip=172.18.0.4 ו־fd.cport=59156.
- fd.sip=172.18.0.2 ו־fd.sport=8080.
- fd.rport היה 59156, ולא 8080 כפי שהכלל המקורי הניח.

תיקנו את הכלל לשדות client/server, הסרנו את כלל האבחון ואימתנו שחזור.
אין להסיק מהדוגמה ש־remote תמיד מייצג לקוח; הלקח הוא לבדוק את השדות באירוע שנאסף.

ב[זוג האירועים השמור](../artifacts/falco-preflight/normal-pair-example.jsonl), פתיחת הקובץ קדמה לחיבור ב־0.023760532 שניות.
המזהים המלאים תואמים ל־orders-api והשרת תואם ל־allowed-api.
connect החזיר EINPROGRESS/-115; לאחר מכן האפליקציה קיבלה HTTP 200.
EINPROGRESS מתאר ניסיון שטרם הסתיים באותה נקודה, ואינו כשלעצמו הוכחה לכישלון הבקשה.

## 11. שלב 4 — המדיניות הראשונית
נוצר config/policy.baseline.yaml בגרסה baseline-1. הוא הצהרה עבור המתאם העתידי ואינו נאכף עדיין.

| הגדרה | בחירה |
|---|---|
| תחום הניטור | orders-api לפי המזהה המלא |
| קובץ רגיש מדומה | /run/demo-secrets/credentials-demo.json |
| יעד צפוי | allowed-api, כתובת 172.18.0.2 בזמן האימות, TCP 8080 |
| חלון חיפוש | פתיחת קובץ לפני חיבור, 0 < הפרש הזמן <= 60 שניות |
| זהות לחיבור ראיות | אותה ריצת חיישן, אותו host ואותו מזהה קונטיינר מלא |
| PID זהה | אינו נדרש |
| חריגי תחזוקה | אין בגרסה הראשונית |

רשומת היעד כוללת את זהות השירות ואת המזהה המלא כנתוני הקשר, ואת צירוף IP/פורט/פרוטוקול להשוואה לראיית רשת.
אירוע connect אינו מספק בהכרח את זהות קונטיינר היעד; מיפוי הסביבה נחוץ כדי להסביר למי שייכת הכתובת.
המזהים והכתובות החיים אומתו מול הצילום לפני יצירת המדיניות.
שינוי בקונטיינרים או בכתובות מחייב צילום חדש ואימות של התאמת המדיניות; הקובץ אינו מתעדכן אוטומטית.

Falco אוסף גם חיבור ליעד צפוי. איננו רוצים לאבד את הראיה; המתאם העתידי ישווה אותה למדיניות.
lab-sink אינו ברשימת היעדים הצפויים. עצם היעדרו אינו מוכיח תקיפה: נדרש גם רצף מתאים והקשר לחקירה.
שם תהליך כמו python אינו מעניק אמון אוטומטי.

~~~bash
cat config/policy.baseline.yaml
~~~

תרגיל: אותו orders-api פותח את הקובץ ואז פונה ל־172.18.0.3:8080 אחרי 10 שניות.
נבא את ההחלטה לפי המדיניות הנוכחית, ואיך היא תשתנה אם נוסיף את הצירוף הזה לרשימת היעדים הצפויים.
זהו תרגיל חשיבה; עדיין אין מנתח שמפיק החלטה בפועל.

## 12. כללי הפרויקט lab-1 — מוכנים להפעלה
נוצר falco/rules.yaml, ושני הכללים עברו Falco --validate ב־0.45.0. Compose עבר אימות תצורה.
החיישן הקיים טרם הופעל מחדש עם הכללים האלה; האימות הוא תחבירי, לא הוכחת איסוף חי.

- list היא רשימת ערכים: מזהי קונטיינרים או נתיבי קבצים.
- macro הוא תנאי משותף בעל שם: lab_monitored_container בודק שהאירוע הגיע מקונטיינר המנוטר.
- rule משלב סוג פעולה, תנאים ופלט ראיות.

הסינון משתמש במזהה המקוצר שמגיע מ־cgroups, כדי לא לתלות את עצם האיסוף בהשלמת המטא־דאטה.
הפלט כולל גם container.full_id, שנדרש למתאם העתידי. אם הוא חסר, נציג בעיית נתונים ולא נחבר אוטומטית את הראיות.
במעבדה המצומצמת אומתה ייחודיות המזהה המקוצר מול שלושת המזהים המלאים בצילום. זו אינה הבטחת ייחודיות בכל סביבה.
המדיניות והכללים הם קבצים נפרדים; Falco אינו קורא את קובץ המדיניות. שינוי זהות מחייב עדכון ואימות של שניהם.

כלל הקובץ אוסף פתיחה מוצלחת המאפשרת קריאה של הנתיב המדומה.
כלל הרשת אוסף connect TCP מכל פורט ויעד מתוך הקונטיינר המנוטר, כולל יעד צפוי, כתובות פרטיות ו־loopback.
אין סינון לפי שם python ואין החרגת allowed-api בשלב האיסוף.

המתאם משתמש בעותק המדיניות שנשמר בכל הקלטה, ולא בקובץ המדיניות הנוכחי אוטומטית.
שדה draft_not_enforced בעותקים ההיסטוריים מתעד את מצב המדיניות בעת ההקלטה; המתאם מבצע כעת ניתוח offline של התוכן.
הוא אינו חוסם פעולות ואינו מחליף את Falco כחיישן.

### אימות התוצאות
scripts/evaluate_recordings.py מפעיל קודם את המתאם ורק לאחר מכן קורא תוויות לצורך השוואה.
נבדקו שמונה ההקלטות שהושלמו, עם המדיניות השמורה בכל אחת:
B1=0, S1=1, B2=0, B3=0, S2=0, B4=0, S3=1, B5=0.
כל שמונה התוצאות תאמו את הציפיות, ללא שגיאות נתונים.
S2=0 נשאר מגבלת כיסוי ידועה, לא הצלחה בזיהוי כל פעילות חשודה.
זהו אימות על תרחישים מבוקרים, לא מדד דיוק כללי; ההקלטות כוללות baseline-2 ו־baseline-3.

27 בדיקות סינתטיות עברו: גבול 60 שניות והחריגה בננו־שנייה, סדר הפוך/שווה/מעורב,
כפילויות, כמה פתיחות וחיבורים, חלון חיפוש נע, שדות חסרים, תוצאות חיבור וחריגים ברמת זוג.
שלוש בדיקות אינטגרציה נוספות עברו: קובץ ששונה נדחה, שינוי ריצת חיישן נדחה,
והמתאם פעל גם כשהתווית ולוג האפליקציה בעותק בדיקה הוחלפו בטקסט בלתי תקין.
דוגמאות הגבול מסומנות כסינתטיות בקובץ tests/test_correlator.py ואינן מוצגות כראיות חיות.
הבדיקות קיימות כקוד, לא רק כבדיקות ידניות.

~~~bash
python3 -m unittest discover -s tests -v
python3 scripts/evaluate_recordings.py
~~~

דוח ההשוואה נשמר ב־artifacts/reports/evaluation.json.
התלות הנוספת היא PyYAML 6.0.1, הגרסה שהותקנה ונבדקה בסביבה; היא נרשמה ב־requirements.txt.
שלב 6 הושלם לגרסה הראשונה. שלב 7 התחיל עם בדיקות הגבול וה־replay; טרם נבדק שיפור תחזוקה לפני/אחרי או דיוק בסביבה אחרת.

## 21. חריג תחזוקה — השוואה על אותה הקלטה
תרחיש M1 הוגדר מראש כפעולת תחזוקה מורשית בתרגיל. הפקודה היא python - maintenance-demo, עם UID 10001 בתוך orders-api.
הקלטת artifacts/recordings/M1-20261006T060525477191Z הושלמה וכל בדיקות האיסוף עברו.
לא מדובר באימות הרשאה אמיתי: ההרשאה היא הנחה מפורשת של התרחיש.
הסימולציה קוראת את הקובץ המדומה ופונה ל־lab-sink בלי לשלוח את תוכנו.

המדיניות הרגילה הפיקה רצף אחד — התרעת שווא לפי הגדרת התרחיש.
config/policy.maintenance.yaml מוסיפה חריג demo-maintenance-pair עם קונטיינר מלא, UID, פקודות שתי הפעולות, נתיב וצירוף יעד מדויק.
baseline נשארה ללא חריג; הגרסה החלופית היא maintenance-1.

אפשר להחיל במפורש מדיניות חלופית על הקלטה סגורה:
~~~bash
python3 scripts/detect_recording.py artifacts/recordings/M1-20261006T060525477191Z
python3 scripts/detect_recording.py artifacts/recordings/M1-20261006T060525477191Z --policy config/policy.maintenance.yaml
python3 scripts/evaluate_maintenance.py
~~~

--policy אינו משנה את הקלטת המקור או את המדיניות שנשמרה איתה.
הדוח מציין recorded_policy_version, policy_source ו־evaluated_policy_sha256.
ללא --output, מדיניות חלופית מקבלת תת־תיקיית דוח עם גיבוב, כדי לשמור את הדוח הרגיל.
report.md מציג כעת גם זוגות ראיות מוחרגים, מזהה החריג ושורות המקור.

על אותה הקלטת M1: לפני 1, אחרי 0, עם זוג מוחרג אחד וללא שגיאות נתונים.
S1 ו־S3 נשארו 1 כל אחד. שאר התרחישים נשארו 0; S2 נשאר מגבלת כיסוי.
דוח ההשוואה: artifacts/reports/maintenance-comparison.json.
38 בדיקות עברו, כולל שינויי פקודה/UID/פורט/קונטיינר וזוג מוחרג שאינו מסתיר זוג אחר.

תוצאות ברמת תשעת תרחישי התרגיל:
- לפני: TP=2, FP=1, FN=1, TN=5.
- אחרי: TP=2, FP=0, FN=1, TN=6.
התוויות נקבעות במעריך בלבד. זו ספירה על סימולציות ידועות, לא מדד דיוק על תקיפות אמיתיות או סביבה אחרת.
התאמה לציפייה S2=0 אינה מבטלת את ההחמצה שלו ביחס לרצף החשוד שהתרגיל מדמה.

מגבלה קריטית: תוקף שיחקה בדיוק את הפקודה, UID ושאר הפרטים יכול ליהנות מהחריג.
החריג אינו מאמת זהות אדם או הרשאה, אינו בודק תוכן HTTP ואינו מעניק אמון גורף ב־Python.
בדיקה מפורשת של מגבלת החיקוי נוספה לטסטים.
שלבי הערכת הליבה ושיפור התחזוקה הושלמו להיקף התרחישים שנבדקו; נותר תיעוד סופי ודמו.
